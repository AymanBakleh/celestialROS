# What is going on in this workspace

This repository is a ROS 2 workspace for a telescope control system built around a camera feed, a GUI, and a mount driver. The project is organized as a standard colcon workspace with multiple Python ROS packages under src/ and build/install artifacts generated by colcon.

## High-level purpose

The system is designed to let a user:

- view a live camera feed from a telescope or astronomy camera,
- optionally run object detection on that feed,
- select a target such as the Moon,
- send a tracking or GOTO command to a telescope mount,
- and monitor the mount state.

In short, this is a telescope/astronomy control interface plus a ROS bridge to actual telescope hardware.

## Workspace structure

At the top level:

- src/ contains the ROS packages
- build/ contains colcon build artifacts
- install/ contains generated ROS environment setup files
- log/ contains colcon logs from builds
- README.md describes quick setup and usage
- INSTALL.md explains installation steps and Docker setup
- docker-launch.sh runs the GUI in a Docker container
- run_gui.sh launches the GUI from a built workspace
- install-zwo-drivers.sh installs the ZWO camera driver stack

## ROS packages in this workspace

### 1) telescope_camera

This package creates the camera driver node:

- package name: telescope_camera
- executable: zwo_camera_node
- file: src/telescope_camera/telescope_camera/camera_node.py

What it does:

- initializes a ZWO ASI camera if the ZWO SDK is available,
- otherwise falls back to a generic V4L2 camera device such as /dev/video0,
- captures frames at a configured rate,
- converts them to ROS Image messages,
- publishes them on /camera/image_raw.

This is the feed source for the GUI.

### 2) telescope_gui

This package is the main user-facing application:

- package name: telescope_gui
- executable: gui_node
- file: src/telescope_gui/telescope_gui/gui_node.py

What it does:

- creates a PyQt5 desktop UI,
- subscribes to /camera/image_raw,
- displays the live camera stream in a QLabel,
- allows the user to select "Remote Control" or "Stand Alone" mode,
- has a "Go To Moon" button,
- can optionally load an ONNX YOLO model for inference overlays,
- publishes target requests to /skyview/request.

This is the part the user sees. It is effectively the front-end orchestration layer.

### 3) skyview

This package is a small forwarding node:

- package name: skyview
- executable: skyview_node
- file: src/skyview/skyview/skyview_node.py

What it does:

- subscribes to /skyview/request,
- republishes the same target as /skyview/target.

This exists as a simple routing layer so the GUI can publish a request without directly depending on the mount driver interface.

### 4) telescope_driver

This package is the hardware bridge to the telescope mount:

- package name: telescope_driver
- executable: telescope_driver
- file: src/telescope_driver/telescope_driver/telescope_driver.py

What it does:

- connects to the telescope mount through serial or WiFi,
- subscribes to both /stellarium/target and /skyview/target,
- converts target data into mount GOTO commands,
- sends JSON commands to the mount hardware,
- reads feedback from the mount,
- publishes /telescope/hardware_joint_states for visualization,
- publishes /telescope/state with the current RA/DEC.

This is the robot control layer. It communicates with the physical mount.

## Launch flow

The launch file for the main GUI stack is:

- src/telescope_gui/launch/gui.launch.py

This file starts four nodes:

1. zwo_camera_node from telescope_camera
2. skyview_node from skyview
3. telescope_driver from telescope_driver
4. gui_node from telescope_gui

This startup order matters:

- the camera publishes frames,
- the GUI consumes those frames,
- the GUI emits a target request,
- skyview forwards the request,
- the telescope driver translates it into a mount command.

## Data flow

The runtime pipeline looks like this:

- Camera captures raw image
  -> publishes on /camera/image_raw
- GUI receives image
  -> displays it
  -> optionally runs YOLO inference
  -> publishes a target on /skyview/request
- Skyview node relays target to /skyview/target
- Telescope driver subscribes to /skyview/target
  -> converts RA/DEC into a mount command
  -> sends the command to the mount
- Mount hardware provides feedback
  -> driver publishes /telescope/state and joint states

This is a typical ROS control architecture: raw sensor input, UI + processing, command dispatch, hardware bridge, and state feedback.

## Important project conventions

### Geolocation

The GUI code contains observatory coordinates for Damascus, Syria:

- latitude: 33.5138
- longitude: 36.2765
- elevation: 680.0 m
- timezone: Asia/Damascus

This is used when the user chooses the Moon target and the code calculates the Moon position relative to the local site.

### Camera support

The camera package is designed to support:

- ZWO ASI cameras via the Python zwoasi library,
- fallback to generic USB camera devices via OpenCV V4L2.

This makes the system flexible in both native hardware and Docker environments.

### GUI features

The GUI includes:

- mode selection between laptop control and standalone Raspberry Pi control,
- a Go To Moon button,
- optional YOLO inference overlay on the live image,
- a status label indicating whether inference is active.

### Mount protocol

The driver expects commands in JSON format and sends mount commands with a command type T field. The logic includes:

- serial communication support,
- WiFi TCP socket support,
- protection against duplicate target spam,
- filtering of targets that are already near the current mount position.

This workspace is a ROS 2 telescope-control application that captures camera video, overlays optional AI detection, sends telescope target requests through a skyview router, and drives a real telescope mount over serial or WiFi.
